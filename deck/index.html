The scenarios that matter are the ones you can't stage alone

  • Anything with two or more participants talking at the same time
  • A warm transfer, then a supervisor listening in
  • A customer who switches language mid-call
  • A network that dies during the call

Every one of those needs people, phones, and an afternoon. So they get tested once, by hand, badly — and then never again.

Look at QA on "tested once, by hand, badly". This slide is for them.

Deliberately no counts — the point is "more than one party", not a number.

Synthetic participants that stand in for real people

One browser tab is one understudy. It injects a synthetic microphone (text-to-speech) and a synthetic camera, then joins as a real party over the real signalling.

  • It touches only public seams — the same browser APIs any customer's browser usesNever application internals. That keeps the test honest and lets it survive the app being rewritten underneath it.
  • The platform is the system under test — Understudy drives every party, customer and agent
  • Voice, webchat and SingleMeet — inbound and outbound

"It isn't a mock. There's a real SIP registration, a real FreeSWITCH conference, a real LiveKit room. The only synthetic thing is the human."

The inversion

Understudy ships a skill. A coding agent working a ticket loads it, stands up the exact call the ticket describes, and asserts on what came back.

# the agent does this, not me

# and this, when it thinks it is done
pnpm understudy run scenarios/voice/r3a-healthfirst-inbound \
    --env qa --execute --check-baseline
An agent that can only read code is guessing. An agent that can place a call and listen to what came back is verifying.

    --env qa --execute --headed --hold

Four people in one SingleMeet room — English, Spanish and French — with live captions for all of them.

Nobody in this room could stage that in an afternoon. It is one command, and it is repeatable tomorrow.

Prerequisites, once: set -a; source secrets/qa.env; set +a then pnpm bundle:runtime && pnpm bundle:meet. No captured session needed — all four parties are standalone, so nobody signs into a console.

Watch one window, not all four. With --headed each party now renders a tile grid of the whole room — itself plus the other three — with a caption strip underneath. Maximise one window and let the others sit behind it.

--hold keeps the windows open until you press Enter. Use it.

"Riley opens the room, then Sofía, Pierre and Dana join it. Four phases: clean alternation, then rapid interjections, then long turns, then a closing round."

What it is really for: measuring caption speaker attribution — one mixed speech stream serves the whole room, so who said what is inferred afterwards. Each caption in the strip is tagged with the identity the worker attributed it to, so a misattribution is visible on screen. Say that if anyone asks why the script sounds so stilted.

What the old console could never tell us

livebeaconing normally
silentexpected, and not heard from
endedsigned out cleanly, with a reason
vanishedstopped mid-shift with no goodbye

These are liveness states — whether we are still hearing from a console at all. Nothing to do with agent status, which is about what the person is doing.

"A console whose network has gone doesn't report the outage. It stops reporting. The board gets quieter while people can't work. That's the failure mode this whole thing exists for."

Be explicit that this is not presence/agent status — that confusion is the one thing this slide has to prevent.

Of every agent console running in production right now —

what percentage is the focused window?

ASK THE ROOM. Take guesses out loud. Don't move on until three people have answered. People guess 40–60%.

The answer, delivered verbally: 7% are focused. 69% are not even visible. Measured across 1,387 real consoles.

"A browser throttles a hidden tab's timers to about one a minute. So a console behind a spreadsheet beacons late and looks exactly like one in trouble. On a fleet this size that's forty of eighty-six quiet consoles who are completely fine — and saying so is forty phone calls not made."

The falsifier is the interesting part: a proposal that can't say what would prove it wrong is an opinion, not a finding.

Why the model never gets to press the button

  • It suggests. People decide. The engine acts.Whatever runs is something a human already reviewed, so a bad suggestion is a wasted minute rather than an incident.
  • Pick from a list before writing prose"Which of these known problems is this?" — with "none of them" always allowed. Free text is a fallback, and it is labelled as unverified wherever it appears.
  • "Certain" and "probably" are different kinds of thingNot two ends of one scale — otherwise a 97% guess quietly starts behaving like a fact.
  • Every suggestion is scored afterwardsShown, accepted, run, and then: did it actually work? A suggestion that keeps working becomes a rule we ship. That is how it improves without a model anywhere near the runtime.

"The learning lands as reviewed, versioned, switch-off-able data — not as a model that quietly changed its mind."

Tomorrow hook: that scoring ledger is the one piece of shared AI platform I'd argue for.
